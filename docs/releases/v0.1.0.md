# IronMule v0.1.0

Release-note artifact for the first public release. This file is prepared for a GitHub release; it does not publish anything by itself.

## What IronMule is

IronMule is an adaptive MLX inference runtime for local LLMs on Apple Silicon. It measures optimizations on your Mac and only keeps them when they are faster and remain correct.

Its public runtime makes the execution plan and service mode explicit, then reports the trade-offs. It includes prefix KV caching, grouped batch-1 execution, LLM inference telemetry, correctness checks, and a hardware/framework/model validity fingerprint.

**Measured, not assumed.** The evidence is local and bounded. See [`docs/LIMITS.md`](../LIMITS.md) and [`research/LEDGER.md`](../../research/LEDGER.md) before applying a result to another Mac, local LLM, model, quantisation, workload, or MLX build.

## Key measured results

The following values are copied from E10, E12, E15, and E16. They are not forecasts.

### Grouped batch-1 service mode (E16)

E16 used 40 independent OS processes, five per condition:

| Workload | Throughput | Median latency | Tail latency (p95) | Service TTFT |
| :-- | --: | --: | --: | --: |
| homogeneous | `+16.4 … +17.2%` | `+27%` | `−16%` | ~800 → ~87 ms |
| heterogeneous | `+15.6 … +15.8%` | `+27%` | `−15%` | ~800 → ~87 ms |
| staggered arrivals | `+15.1%` | `+26%` | `−8%` | ~690 → ~88 ms |
| short answers | `+9.2%` | `+54%` | `−9%` | — |

E16 reports zero correctness failures across 40 processes. Its frozen verdict is `CONFOUNDED_BY_PROCESS_STATE`; its substantive reading is replication. Grouping does not make an individual request faster: median latency worsens while tail latency and first-token latency improve.

### Prefix KV reuse

- E10: `−37.82%` end-to-end session time at a 66.8% shared prefix; two independent sessions produced identical tokens for all 12 requests.
- E12: TTFT ratios `0.401` at prefix 276, `0.238` at 768, `0.169` at 1024, `0.141` at 1280, and `0.094` at 2048.
- E12: within the declared chunked execution plan, reuse was bit exact across 756 requests and 14,369 decode steps in five independent processes.

These session and prefix results describe different workloads and are not interchangeable.

### Negative findings kept in the release

Speculative decoding was `2.9×` slower with acceptance `0.17` per drafted token. True tensor batching changed tokens at batch 8 and is not shipped. Projection fusion in decode was neutral. The dispatch-overhead hypothesis was rejected, and kernel counts were retired because MLX exposes no machine-readable dispatch counter.

## Installation

```bash
pip install ironmule
```

IronMule requires Python 3.10+, an Apple silicon Mac, MLX-compatible local runtime dependencies, and a model snapshot supplied by the user. The package does not download or redistribute model weights.

For development from a checkout:

```bash
git clone https://github.com/Tobayko/IronMule.git
cd IronMule
python -m pip install -e ".[dev]"
```

## How to benchmark

Check prerequisites:

```bash
ironmule doctor
```

Run the local benchmark against the available compatible setup:

```bash
ironmule benchmark
```

For the repository's module form:

```bash
python -m ironmule.benchmark
```

Record the Mac model, Apple chip, RAM, macOS, Python, MLX, mlx_lm, model revision, quantisation, context, workload, warmup, repetitions, baseline, IronMule result, and correctness outcome. Submit a reproducible result through the [benchmark issue template](../../.github/ISSUE_TEMPLATE/benchmark_submission.md).

## Known limitations

The complete validity domain is: `mlx-community/gemma-3-4b-it-4bit` revision `93724907`; 4-bit group size 64; MLX `0.32.0`; mlx_lm `0.31.3`; Apple M1 Max, 32 GB unified memory, 32 GPU cores; AC power; greedy decoding (`temperature = 0`); batch 1 per execution; contexts 276–2048 tokens; and up to 8 concurrent requests. Nothing outside this box is claimed without re-measurement.

Important limitations from [`docs/LIMITS.md`](../LIMITS.md):

- Group width is capped at 4; width 8 regressed in E14b and E2/E3 independently.
- One `serve()` call allocates to its longest prompt and refuses capacity above 8192.
- Grouping helps only when groups fill; 2–3 token answers reduced realised width to 1.83 and the gain fell below threshold in E15/E16.
- Median latency worsens by 26% to 54%, depending on workload.
- Ragged prompt lengths within one group and sustained load are untested.
- E13's `1.14` accuracy-point quality bound was measured on a contaminated public benchmark and only for extractive question answering.
- E16's frozen verdict remains `CONFOUNDED_BY_PROCESS_STATE`; the direct accumulation instruments read zero.
- No absolute dispatch time is claimed; MLX exposes no machine-readable dispatch counter.
